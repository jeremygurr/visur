1. What Is Visur?

Visur is a Vim-inspired rich text editor built as a Vert.x event-sourced application. In plain English: it is a server-side Java program that listens for keyboard input from a web browser, edits an in-memory text document, and pushes the rendered result back to the browser via WebSockets—a bidirectional, low-latency protocol that keeps an open connection between browser and server. The rendering happens in the browser using the HTML5 Canvas API—there is no DOM-based editing, no contenteditable, no HTML input fields. Every keystroke, cursor position, and character is computed on the server and painted on a canvas by the browser.

What Are WebSockets?

WebSockets are a networking protocol that lets a browser and a server maintain an open, full-duplex communication channel over a single TCP connection. Unlike the traditional HTTP request/response model—where the browser must send a new request for every piece of data—WebSockets keep the connection alive, allowing both sides to send messages at any time without establishing a new connection. Think of it like a telephone call versus email: with HTTP, you have to pick up the phone, say your piece, and hang up every time. With WebSockets, the line stays open; either party can speak whenever they want. For an editor like Visur, this is essential because every keystroke must reach the server instantly, and every screen update must appear on the canvas without noticeable delay. WebSockets provide that low-latency, bidirectional pipe, making remote editing feel responsive.

It draws inspiration from Vim: the same mode-based editing (normal, insert, replace), the same key-driven command language (5j = move down five lines, w = forward word), and the same idea that the editor state—cursor position, selection, current mode—is the single source of truth.

The key difference from Vim: everything happens over a network. Vim runs locally in a terminal. Visur runs on a server, and the browser is the display terminal. This is an editor as a service architecture.

2. The Architecture—Three Verticles, One Event Bus

The core of Visur is Vert.x, a reactive toolkit for building event-driven applications on the JVM. Vert.x uses the concept of verticles—units of deployable code that communicate via an event bus. Each verticle listens for messages on specific "addresses" and can send messages to other addresses.

Visur deploys exactly three verticles, each responsible for a distinct concern:

Verticle 1: KeyWasPressedVerticle — The Editor's Brain

This verticle receives keyboard events from the browser on the event bus address "keyWasPressed". Its job is to interpret the keystroke and mutate the editor model. The source is KeyWasPressedVerticle.java.

Verticle 2: ModelWasChangedVerticle — The View Builder

This verticle listens on "modelWasChanged". Whenever another verticle (or the KeyWasPressedVerticle itself) posts a modelWasChanged event, this verticle:

  1. Reads the current editor state from the EditorModelCoupler (the shared state hub).
  2. Builds a View object containing the full editor state: content, cursor position, mode, submode, quantum, span, canvas start/end, search target, command state.
  3. Serializes it to JSON and sends it on the event bus address "viewWasChanged".

The browser's visur.js receives this JSON and uses it to redraw the canvas: re-paint all text, move the cursor, update the mode indicator in the footer.

Verticle 3: CanvasWasChangedVerticle — The Viewport Manager

This verticle listens on "canvasWasChanged". It receives the browser's canvas width and height whenever the window is resized or first connected. It:

  1. Stores the canvas dimensions in the EditorModelCoupler.
  2. Uses those dimensions (along with the newline index list) to compute canvasStart and canvasEnd—the visible region of the document.
  3. Posts modelWasChanged so the ModelWasChangedVerticle sends a fresh View that includes the updated canvas boundaries.

Without this verticle, the editor would not handle window resizing—text would be clipped at the old viewport boundaries.

Services Created at Startup

The ServiceHolder creates all shared services exactly once at startup. These are static singleton references—every verticle accesses them through ServiceHolder.XXX:

  • editorContentService — reads and writes editor content (text, newline indices, global variables, canvas dimensions)
  • editorModelCoupler — the central state hub (a LocalMap keyed by EditorModelKey enum values)
  • commandCompileService — parses keystrokes into Words (CommandCompileService)
  • commandExecutionService — executes compiled commands as Operators (CommandExecutionService)
  • commandStateService — manages the bottom command-line state
  • modeSwitchService — handles mode and submode transitions
  • initializerService — one-time editor initialization
Key design note: The EditorModelCoupler uses a LocalMap<EditorModelKey, Object> from Vert.x's shared data API. This means all three verticles share the exact same in-memory state object. There is no replication, no synchronization needed—they are all in the same JVM and share the same LocalMap. This is why the coupling is "tight" and the architecture is simple.

4. The Four Event Bus Addresses

All communication between the browser and server, and between verticles, happens through Vert.x's event bus using four addresses defined in the BusEvent enum:

AddressDirectionWho sendsWho receives
"canvasWasChanged" Browser → Server Browser JS (on connect + resize) CanvasWasChangedVerticle
"keyWasPressed" Browser → Server Browser JS (on keydown) KeyWasPressedVerticle
"modelWasChanged" Server → Server (or Server → Browser) KeyWasPressedVerticle, CanvasWasChangedVerticle ModelWasChangedVerticle
"viewWasChanged" Server → Browser ModelWasChangedVerticle Browser JS (sockJS on viewWasChanged)

5. Building and Running Visur

The project uses Gradle with Kotlin DSL (build.gradle.kts). The critical dependencies from build.gradle.kts are:

  • io.vertx:vertx-web:4.4.4 — HTTP server, routing
  • io.vertx:vertx-rx-java3:4.4.4 — reactive Java bindings
  • io.vertx:vertx-tcp-eventbus-bridge:4.4.4 — WebSocket event bus bridge (used for browser ↔ server communication)

The build produces a fat JAR via the Shadow plugin (com.github.johnrengelman.shadow), which bundles all dependencies into a single runnable JAR.

Hands-on commands (type these in your terminal):

cd /Users/jaredgurr/repos/visur

./gradlew fatJar

java -jar build/libs/visur-1.0.0-SNAPSHOT-fat.jar

After running, open http://localhost:8888/static/visur.html in your browser. You should see a canvas with the default text "The quick brown fox jumps over the lazy dog" and a yellow cursor. The editor starts in Normal mode (you can type i to enter Insert mode).

7. Shared State: The EditorModelCoupler

Perhaps the single most important file in the entire codebase is EditorModelCoupler.java. It is the single source of truth for the editor's entire state—every verticle reads from it and writes to it.

Internally, it holds a LocalMap<EditorModelKey, Object> where the keys are an enum (EditorModelKey) defining every piece of state:

  • editorContent — the full text being edited
  • nextLineIndices — computed newline positions (the nl global variable)
  • cx, cy, ca — cursor coordinates (local X, local Y, absolute)
  • editorMode — Normal, Replace, or Insert
  • editorSubmode — Span, Scope, SearchForward, SearchBackward, etc.
  • span — current selection width
  • canvasStart, canvasEnd — visible region
  • cursorQuantum, cursorQuantumStart, cursorQuantumEnd — current quantum (character/line/regex/document)
  • scopeQuantum — scope type for search operations
  • keymapMap — key bindings organized by submode
  • isInCommandState — boolean for command-line mode
  • commandStateContent, commandCursor — command-line buffer
  • executionDataStack — stack for submode operations (e.g., search targets)
  • Global variables: nl, cx, cy, ca, span, cursorQuantum, scopeQuantum, previousSearchTarget
Important: The EditorModelCoupler is a static field on ServiceHolder. This is a design pattern that gives all verticles direct access to the same state object. It is not thread-safe in the traditional Java sense—Vert.x is single-threaded per event loop, so this works because only one thread ever touches the data at a time. If you refactor to use threads, this pattern breaks.

8. Key Takeaways

Before moving to Lesson 2, make sure you can answer these questions:

  • What is Visur? A Vim-inspired rich text editor running as a server, with the browser as a thin rendering terminal.
  • How many verticles are there? Three: KeyWasPressedVerticle (editing logic), ModelWasChangedVerticle (view building), CanvasWasChangedVerticle (viewport management).
  • How does the browser communicate with the server? Via WebSocket through Vert.x's SockJS bridge, using four event bus addresses.
  • What is the single source of truth for editor state? The EditorModelCoupler, a shared LocalMap<EditorModelKey, Object>.
  • How do you build and run it? ./gradlew fatJar then java -jar build/libs/visur-*-fat.jar.
  • What is the request loop? Browser sends keystroke → server mutates state → server sends View JSON → browser redraws canvas.
