1. What Is Visur?

Visur is a Vim-inspired text editor built as a Vert.x event-driven application. In plain English: it is a server-side Java program that listens for keyboard input from a web browser, edits an in-memory text document, and pushes the result back to the browser over a SockJS/WebSocket connection—a bidirectional, low-latency protocol that keeps an open connection between browser and server. The drawing happens in the browser using the HTML5 Canvas API—there is no DOM-based editing, no contenteditable, no HTML input fields. The document state—content, cursor, mode, and which slice of the document is visible—is computed on the server; the browser only paints glyphs at coordinates its own canvas code derives from that state (see visur.js). Editor state lives only in memory, in a Vert.x LocalMap: nothing is persisted, so “event-sourced” in the project notes means “state mutated by events”, not an event log you could replay.

What Are WebSockets?

WebSockets are a networking protocol that lets a browser and a server maintain an open, full-duplex communication channel over a single TCP connection. Unlike the traditional HTTP request/response model—where the browser must send a new request for every piece of data—WebSockets keep the connection alive, allowing both sides to send messages at any time without establishing a new connection. Think of it like a telephone call versus email: with HTTP, you have to pick up the phone, say your piece, and hang up every time. With WebSockets, the line stays open; either party can speak whenever they want. For an editor like Visur, this is essential because every keystroke must reach the server instantly, and every screen update must appear on the canvas without noticeable delay. WebSockets provide that low-latency, bidirectional pipe, making remote editing feel responsive. Visur reaches the same pipe through Vert.x's SockJS bridge, which prefers a WebSocket transport and falls back to HTTP streaming/long-polling when a WebSocket cannot be established (MainVerticle.java, visur.js).

It draws inspiration from Vim: mode-based editing, a key-driven command language, and the same idea that the editor state—cursor position, selection, current mode—is the single source of truth.

Three details of that inheritance are easy to get wrong, because Visur splits what Vim calls a “mode” into a mode and a submode:

  • Modes come from EditorMode.java: navigate (Vim's Normal mode), insert, and reading (declared, not implemented). Replace is not a mode—it is one of the values of EditorSubmode.java (replace, span, quantumStart, quantumEnd, searchForward, searchBackward, changeScope).
  • No count prefixes. 5j does not mean “down five lines”. In navigate mode j is bound to the fixed command 0 1 relativeMove (InitializerService.java), and nothing buffers digits between keystrokes—the keyBuffer field of EditorModelKey is declared but never read or written. Digits are only consumed as a span width, inside span submode (SpanSubmodeHandler.java).
  • w is a quantum selector, not “forward word”. w switches the cursor's unit of movement and selection to the word quantum, via ChangeCursorQuantumHandler.java. The keys are q→character, w→word, e→line, r→document (InitializerService.java).

The key difference from Vim: everything happens over a network. Vim runs locally in a terminal. Visur runs on a server, and the browser is the display terminal. This is an editor as a service architecture.

2. The Architecture—Three Verticles, One Event Bus

The core of Visur is Vert.x, a reactive toolkit for building event-driven applications on the JVM. Vert.x uses the concept of verticles—units of deployable code that communicate via an event bus. Each verticle listens for messages on specific "addresses" and can send messages to other addresses.

Visur deploys exactly three verticles, each responsible for a distinct concern:

Verticle 1: KeyWasPressedVerticle — The Editor's Brain

This verticle receives keyboard events from the browser on the event bus address "keyWasPressed". Its job is to interpret the keystroke and mutate the editor model. The source is KeyWasPressedVerticle.java.

Verticle 2: ModelWasChangedVerticle — The View Builder

This verticle listens on "modelWasChanged". Whenever another verticle (or the KeyWasPressedVerticle itself) posts a modelWasChanged event, this verticle:

  1. Reads the current editor state from the EditorModelCoupler (the shared state hub).
  2. Builds a View object—which holds only two fields, ca and editorContent—then fills in the rest of the JSON directly from the coupler in toJson(): span, canvasStart, canvasEnd, cursorQuantumStart/End, editorMode, editorSubmode, cursorQuantum, scopeQuantum, isAtQuantumStart, isInCommandState, commandStateContent, commandCursor, plus searchTarget (only while in a search submode).
  3. Sends that JSON on the event bus address "viewWasChanged" (handleChange()).

The browser's visur.js receives this JSON and uses it to redraw the canvas: re-paint all text, move the cursor, update the mode indicator in the footer.

Verticle 3: CanvasWasChangedVerticle — The Viewport Manager

This verticle listens on "canvasWasChanged". The browser sends the canvas width and height once, right after it connects (there is no resize listener—more on that below). It:

  1. Stores the canvas dimensions in the EditorModelCoupler (source).
  2. Prints a debug listing of the document's lines. Careful: that loop indexes the newline list with cy (the cursor's line) instead of the loop counter, so it logs the cursor's line N times rather than logging every line (source).
  3. Posts modelWasChanged so the ModelWasChangedVerticle sends a fresh View that carries the new dimensions (source).

What it does not do is compute the visible region: it never touches canvasStart. canvasStart is maintained by the coupler's scrolling helpers (putCanvasStart, incrementCanvasStart/decrementCanvasStart), while canvasEnd is derived on demand from canvas width/height, the newline list and the first visible line fy (getCanvasEnd()).

One real limitation: because canvasWasChanged is sent only inside eb.onopen (visur.js), resizing the browser window does not update the server's notion of the viewport. The canvas element itself grows or shrinks, but the server keeps describing the old rectangle until the page is reloaded.

Services Created at Startup

The ServiceHolder creates all shared services exactly once at startup. These are static singleton references—every verticle accesses them through ServiceHolder.XXX:

  • editorContentService — reads and writes editor content (text, newline indices, global variables, canvas dimensions)
  • editorModelCoupler — the central state hub (a LocalMap keyed by EditorModelKey enum values)
  • commandCompileService — parses command sentences (strings like "0 1 relativeMove") into Word/Operator lists at startup and when submodes produce commands
  • commandExecutionService — runs a compiled command: it walks the operator list and dispatches each op, pulling operands off the execution-data stack
  • commandStateService — edits the bottom command-line buffer (typed characters, backspace, arrows, Enter/Escape)
  • modeSwitchService — created at startup but currently dead code: it is never called, and its execute() body is entirely commented out (source). Mode changes actually happen in ChangeModeOp, which writes editorMode and then pushes a submode.
  • initializerService — one-time editor initialization (its constructor does the work, so creating it is the initialization)
Key design note: The EditorModelCoupler uses a LocalMap<EditorModelKey, Object> from Vert.x's shared data API. This means all three verticles share the exact same in-memory state object. There is no replication—they are all in the same JVM and share the same LocalMap. That is why the coupling is "tight" and the architecture is simple. It also means there is no transaction boundary around a multi-step update; see the threading caveat in section 7.

4. The Four Event Bus Addresses

All communication between the browser and server, and between verticles, happens through Vert.x's event bus using four addresses defined in the BusEvent enum:

AddressDirectionWho sendsWho receives
"canvasWasChanged" Browser → Server Browser JS (once, on connect—not on resize) CanvasWasChangedVerticle
"keyWasPressed" Browser → Server Browser JS (on keydown) KeyWasPressedVerticle
"modelWasChanged" Browser → Server (and permitted Server → Browser) Browser JS (echo sent from eb.onopen, after canvasWasChanged), KeyWasPressedVerticle, CanvasWasChangedVerticle ModelWasChangedVerticle
"viewWasChanged" Server → Browser ModelWasChangedVerticle Browser JS (sockJS on viewWasChanged)

5. Building and Running Visur

The project uses Gradle with Kotlin DSL (build.gradle.kts) and targets Java 16 (source). The dependencies that matter most for this lesson are (source):

  • io.vertx:vertx-web:4.4.4 — HTTP server, routing, and the SockJSHandler that installs the event bus bridge the browser talks to.
  • io.vertx:vertx-rx-java3:4.4.4 — the RxJava 3 bindings; note that every verticle extends io.vertx.rxjava3.core.AbstractVerticle, not the plain core one.
  • io.vertx:vertx-tcp-eventbus-bridge:4.4.4 — declared on the classpath, but not what the browser uses. No TCP bridge is installed anywhere in src/main/java; the browser connects through the SockJS bridge above. The build also pulls in several other Vert.x modules (vertx-web-client, vertx-health-check, vertx-opentelemetry, vertx-shell, vertx-micrometer-metrics, ...) that MainVerticle never touches.

The build can also produce a fat JAR via the Shadow plugin (com.github.johnrengelman.shadow), which bundles all dependencies into one archive with the classifier fat (source). The runnable task for the server, though, is Gradle's run: build.gradle.kts wires it to Vert.x's Launcher with the arguments run com.ple.visur.MainVerticle --redeploy=... (source).

Hands-on commands (type these in your terminal):

cd /Users/jaredgurr/repos/visur

./gradlew run

(There is no fatJar task; the Shadow task is shadowJar, and java -jar build/libs/visur-1.0.0-SNAPSHOT-fat.jar only prints the Vert.x launcher help, because the manifest declares MainVerticle-Verticle while io.vertx.core.Launcher looks for Main-Verticle. If you do want to run the JAR, name the verticle: java -jar build/libs/visur-1.0.0-SNAPSHOT-fat.jar run com.ple.visur.MainVerticle.)

After running, open http://localhost:8888/static/visur.html in your browser (or just http://localhost:8888/, which 302-redirects there—see MainVerticle). You should see a canvas showing the opening of the Declaration of Independence—not sample lorem-ipsum text; the initial content is a long string literal in InitializerService. The footer shows two indicators: NAVIGATE MODE on the left and CHARACTER QUANTUM on the right, and the cursor is a gold (#FFD700) block, because span starts at 1 (mode seeds, footer rendering, cursor drawing). The editor starts in navigate mode (Vim's Normal): press i for Insert mode, Escape to come back.

7. Shared State: The EditorModelCoupler

Perhaps the single most important file in the entire codebase is EditorModelCoupler.java. It is the single source of truth for the editor's entire state—every verticle reads from it and writes to it.

Internally, it holds a LocalMap<EditorModelKey, Object> where the keys are an enum (EditorModelKey). A wrinkle worth knowing before you go hunting through that enum: only some entries are actually used, and the cursor coordinates are not enum keys at all. The live entries are:

  • editorContent — the full text being edited
  • canvasWidth, canvasHeight, canvasStart, fy (first visible line) — the viewport; canvasEnd is computed from these rather than stored
  • editorMode — a value of EditorMode
  • editorSubmodeStack — a Stack<EditorSubmode>; getEditorSubmode() peeks the top, which is why submodes stack
  • modeToKeymap — the KeymapMap used by the KeyWasPressedVerticle (note the enum also declares an unused keymapMap constant; modeToKeymap is the one the getter/setter use)
  • quantumStart, quantumEnd, isAtQuantumStart — bounds of the current cursor quantum
  • quantumNameToQuantum, keyToQuantumName — the quantum registry and the q/w/e/r key mapping
  • isInCommandState, commandStateContent, commandCursor — the command-line buffer
  • executionData — an ExecutionDataStack used by submodes (e.g. the search target being typed)
  • globalVariableMap — a VariableMap holding the visur variables below
  • virtualCX — remembered column, and previousSearchDirectionWasForward — used by n/N
  • lineWrapping — set once to LineWrapping.wrapped at init and never read again (source)

The editor's variables live in that nested VariableMap (the “global variables” of Lesson 10), reachable as getGlobalVar(name): nl (next-line indices), ca (absolute cursor offset), cx/cy (line-relative column / line number), span (0 or 1 quantums), cursorQuantum, scopeQuantum, and previousSearchTarget. nl, ca, cx, cy are created as data-class bricks in InitializerService; getCX(), getCY() and getCA() read them back out of that map (EditorModelCoupler). So “cx/cy/ca are EditorModelKey values” is the wrong mental model: they are variables, fetched by name.

Important: the EditorModelCoupler is a static field on ServiceHolder, so every verticle reads and writes the same state object. A common—but wrong—way to justify that design is “Vert.x is single-threaded, so only one thread touches it at a time”. Two corrections:
  • Each deployVerticle call (MainVerticle) gets its own context with its own event-loop thread, and a Vert.x instance runs many event loops (2 per core by default). Only code inside a single verticle is guaranteed to be single-threaded; these three verticles can run on three different threads.
  • LocalMap is not a plain HashMap: Vert.x's LocalMapImpl is a ConcurrentHashMap underneath, so individual get/put calls are safe.
The real hazard is that multi-step read-modify-write sequences are not atomic—for example getCanvasEnd()'s loop, or the putCX()/putCA() pairs that must stay consistent. Today that survives because handlers are short and each user keystroke is handled in one burst, but it is a real race surface, not a guaranteed-safe design. Don't add blocking work or threads here without addressing it.

8. Key Takeaways

Before moving to Lesson 2, make sure you can answer these questions:

  • What is Visur? A Vim-inspired text editor running as a server, with the browser as a thin rendering terminal.
  • How many verticles are there? Three: KeyWasPressedVerticle (editing logic), ModelWasChangedVerticle (view building), CanvasWasChangedVerticle (viewport size + redraw trigger).
  • How does the browser communicate with the server? Through Vert.x's SockJS bridge (WebSocket transport, HTTP fallbacks) at /eventbus, using four event bus addresses. The bridge permits three inbound addresses (keyWasPressed, canvasWasChanged, modelWasChanged) and two outbound (modelWasChanged, viewWasChanged).
  • What is the single source of truth for editor state? The EditorModelCoupler, a shared LocalMap<EditorModelKey, Object> that also contains a VariableMap of named editor variables (nl, ca, cx, cy, span, ...).
  • How do you build and run it? ./gradlew run (or ./gradlew shadowJar then java -jar build/libs/visur-1.0.0-SNAPSHOT-fat.jar run com.ple.visur.MainVerticle).
  • What is the request loop? Browser sends keystroke → server mutates state → server sends View JSON → browser redraws canvas.
