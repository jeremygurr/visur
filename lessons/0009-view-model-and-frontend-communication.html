The Wire: Viewport Protocol and Two Renderers

Reads ~16 min · Hands-on: trace a viewport declaration and one keystroke

The editor model is server-side; renderers receive complete, viewport-bounded viewWasChanged snapshots. The browser remains a canvas client over SockJS, and terminal/ adds a Rust terminal client over a plain WebSocket. Both paint the same server-laid-out rows; neither owns editor state or decides how text wraps.

Mission Anchor

Lesson 8 followed cursor coordinates inside the editor model. Here we follow the renderer boundary: client input → event bus → editor state → complete view → browser canvas or terminal grid.

Goal this lesson: Name the inbound and outbound addresses, explain the 17-field viewport snapshot, distinguish the browser and terminal transports, and trace startup and one keystroke without confusing layout with painting.

1. Addresses and the Viewport Loop

BusEvent names four current addresses. The directions are asymmetric: clients declare a viewport and send keys; the server publishes a complete view.

viewportWasChanged carries cols and rows in cells, not pixels. Rows exclude renderer chrome. The handler stores the dimensions and triggers a full view; the terminal subtracts its own mode-line row before declaring its grid. The browser computes cell counts from canvas pixels and declares again when its viewport changes. See visur.js and terminal/src/main.rs.

MainVerticle.java permits browser input on viewportWasChanged and keyWasPressed, and output on viewWasChanged. Its /eventbus SockJS bridge is for the browser; /ws is the terminal's WebSocket route.

2. The Snapshot Is Built by View

The old mutable View.ca/View.editorContent holder is gone. Current View is a record: View.of(emc) projects editor state, delegates row layout to Viewport, and render() produces the JSON. The model verticle is a pipe: it publishes that payload on viewWasChanged.

These are exactly 17 fields. editorContent, ca, canvasStart, and canvasEnd are not payload fields. Each row carries its own absolute origin; renderers do not need the document, a wrap table, or a delta. Every message is a complete viewport state. On full: true, discard cached rows; clamp cursor coordinates; if rows are empty, paint a blank screen.

Keep the seam straight. The server lays out and projects cursor position. A renderer neither re-wraps rows nor owns editor state. viewWasChanged is published because every attached renderer needs the same update; point-to-point send would select only one consumer.

3. The Keymap Is Server-Side and Keyed by Submode

Both clients forward key tokens; editing semantics remain on the server. KeyWasPressedVerticle chooses the keymap by the current submode, executes a command when one matches, then triggers modelWasChanged. The keymap arc is unchanged from earlier lessons; the change is that either renderer can send the key.

4. The modelWasChanged Trigger and Published View

A key handler sends the internal modelWasChanged trigger after dispatch. A viewport declaration updates the stored grid and sends the same trigger with {"full":true}. The model verticle then projects the current state and publishes the view. The old browser relay and its extra modelWasChanged bridge permissions are no longer part of the protocol.

The browser bridge permits only key and viewport input and view output. The terminal's socket is a direct pipe to the event bus: frames in both directions use {"address":…,"body":…}. On connection it registers for published views; on close or exception it unregisters. The route is loopback-only at 127.0.0.1:8888/ws, with no SockJS framing, session id, or heartbeat. Source: MainVerticle and terminal/src/transport.rs.

5. Two Renderers, One View

Browser canvas

visur.js keeps the latest view, clears and repaints the canvas, draws the provided row strings, and uses the server-projected cursor row/column. It still owns browser presentation details—font, cell metrics, pixel offsets, canvas painting and HTML status text. It does not wrap the document or send a modelWasChanged echo. Browser traffic remains SockJS through /eventbus.

Rust terminal client

terminal/ is a separate Rust renderer. Its protocol codec consumes the same viewWasChanged envelope; the client keeps a view shadow and cell grid, composes rows, computes row-run damage, and emits terminal escape sequences. It has its own lifecycle and launcher; the root launcher uses an existing server or starts and owns one as needed. ./gradlew run still starts the server by itself. See the component breakdown in the renderer specification.

The client is a stateless painter in the editor sense: its cache is only what it paints, not authoritative document or editing state. It can restart and reconstruct the display from a complete view. Terminal viewport rows exclude the mode line, and resize reports a new viewport then receives a full view.

7. Retrieval Practice: Trace Both Paths

Choose the address for each hop. Browser boot and terminal resize enter through the viewport declaration; a key from either renderer follows the editing path. Each trace ends at the same complete view contract.

Hands-on: Run ./gradlew run and open http://localhost:8888/static/visur.html, or use ./visur to launch the Rust client. Inspect a view and verify rows, origin, cursorRow, cursorCol, and the always-present searchTarget. Resize either client and observe a viewport declaration followed by full: true.

10. Key Takeaways

  • viewportWasChanged declares cell dimensions; viewWasChanged carries a complete, bounded viewport.
  • View projects a record; Viewport lays out the rows; ModelWasChangedVerticle publishes.
  • Rows carry absolute starts and text; clients do not re-wrap, infer editor state, or apply deltas.
  • The browser remains the canvas/SockJS path; the Rust terminal is a second renderer on the loopback WebSocket bus-envelope route.
  • Viewport updates request a full repaint; published view updates reach every attached renderer.
