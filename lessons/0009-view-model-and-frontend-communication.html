Lesson 9 of 10

The Wire: Four Addresses, One Snapshot, One Browser

Reads ~16 min · Hands-on: trace both boot and one keystroke, hop by hop, with instant feedback

Everything lessons 1–8 built lives on the server. This lesson is the only place it can be observed: four event-bus addresses, one JSON snapshot, and a Canvas 2D loop in visur.js. The surprise is that the class called View is not the view model, and the two verticles the itinerary says "broadcast" do not broadcast anything — each one consumes one address and sends a different one, forming a chain.

Mission Anchor

Lesson 8 ended on the wire: how ca, canvasStart, and virtualCX become pixels. This lesson answers the mission's end-to-end question at its last hop: browser → EventBus → server → EventBus → browser.

Goal this lesson: Name the address on the envelope for every hop of a keystroke and of the first paint; say which of the 16 snapshot fields drives the cursor, the highlight, and the footer; and explain why the browser registers a handler for a message the server "only sends to itself".

1. Four Addresses, All Pointing One Way Round

BusEvent is a four-value enum, and each value's comment names its sender and receiver. Read the enum as a ring, not a menu:

Only three addresses are reachable across the wire, and the bridge in MainVerticle permits exactly those, in exactly these directions:

DirectionPermitted addresses
Browser → server (inbound)keyWasPressed · canvasWasChanged · modelWasChanged
Server → browser (outbound)modelWasChanged · viewWasChanged

MainVerticle.java:42–47. The page is served by a 302 from / to /static/visur.html (MainVerticle.java:49–66), and the bridge is mounted at /eventbus (line 50); visur.js connects to http://localhost:8888/eventbus (visur.js:46).

Outbound modelWasChanged is the odd permission. It exists only because visur.js registers a handler for it (visur.js:116), which the bridge turns into a real server-side consumer. §4 shows why that is load-bearing rather than leftover.

Why ca is on the wire but unused. The cursor is transmitted as a quantum range plus span, not as a point. drawCanvas decides the caret from cursorQuantumStart/End and isAtQuantumStart, so the absolute index has no consumer left. It is a field the server computes, ships, and the client discards.

3. The Keymap Is Server-Side and Keyed by Submode

The browser never decides what a key means. It forwards event.key verbatim; the meaning lives in InitializerService.initializeKeymaps(), which builds one Keymap per submode at startup and compiles each binding into a VisurCommand on the spot:

InitializerService.java:186–224 · lines 228–269 · Keymap.java:21–39 · KeymapMap.java:10–22 · EditorSubmode.java:3–12.

KeyWasPressedVerticle.java:14–33 · EditorModelCoupler.java:115–118 · lines 128–130.

Two consequences worth memorising. First, a keystroke that matches nothing still ends with modelWasChanged, so the browser always receives a fresh snapshot — the client is a pure function of the last payload, never a local predictor of the next state. Second, because routing is by submode, releasing control ("navigate" pushSubmode, removeSubmode) is part of the command sentence itself: the handler compiles its own way out.

SpanSubmodeHandler.java:12–25 · SearchForwardSubmodeHandler.java:9–37 · ChangeScopeSubmodeHandler.java:10–21.

4. The modelWasChanged Relay

KeyWasPressedVerticle closes the loop with bus.send(BusEvent.modelWasChanged.name(), null). Vert.x send is point-to-point: it picks exactly one local handler for the address, round-robin. That matters because the bridge adds a second one.

So once a browser page is open, roughly half of the modelWasChanged sends land back in the browser instead of in ModelWasChangedVerticle. The browser's handler then re-sends the same address (visur.js:116–119), which is another point-to-point send through the same two-way choice. The view therefore still updates — it just takes an extra browser round trip whenever the first send was routed to the bridge.

visur.js:116–119 · KeyWasPressedVerticle.java:31 · CanvasWasChangedVerticle.java:34 · MainVerticle.java:46 (the outbound permission that makes the handler legal).

Verified vs. inferred. That the bridge registers a competing consumer, and that send chooses one handler round-robin, are both read from the Vert.x 4.4.4 source. That the browser's re-send was written on purpose as a relay is an inference — the strongest supporting evidence is the otherwise-unnecessary outbound permission for modelWasChanged. Ask the author before repeating the "why".

5. What the Browser Does With the Snapshot

The handler assigns each field to a module-level variable (visur.js:1–11), clears the canvas, and calls drawCanvas(). That function is a single walk over the visible absolute range:

visur.js:136–173 · drawCursor:199–209 · footer:75–107 · visur.html:30–35 (one canvas, two footer divs, three scripts).

Note where canvasWidth comes from in that loop: the browser's own let canvasWidth = Math.floor(canvas.width / cellWidth) (visur.js:29). The payload never carries it. The server keeps a second copy, computed from the numbers the browser sent at startup as (canvas.width − 6) / cellWidth + 1 (visur.js:110–113 → CanvasWasChangedVerticle:15–21), and uses it for scroll and quantum bounds. Two formulas, two owners, one notion of "a line": the wrap agreement between server and client is a coincidence to watch, not a guarantee.

The first paint has its own path. On eb.onopen the browser registers the viewWasChanged handler, registers the modelWasChanged relay, and then sends canvasWasChanged — which is what triggers CanvasWasChangedVerticle → modelWasChanged → viewWasChanged and the first frame. There is no resize listener anywhere in visur.js: the canvas is sized once (visur.js:13–19) and canvasWasChanged is sent once (visur.js:120).

6. Itinerary and Wiki Corrections

Lesson 9's bullets name real types, but three of them mis-state direction or ownership. Trust the source.

The itinerary / wiki saysWhat the code does
View — "the complete editor state snapshot sent to the browser (content, cursor, mode, quantum, span, search target, command state)". The wiki's view.md repeats this field list. View has exactly two fields, ca and editorContent (View.java:3–6). The snapshot is an inline JsonObject of 15 (+1 conditional) fields built in ModelWasChangedVerticle.toJson(), and the one View field that does ship (ca) is never read by the client.
ModelWasChangedVerticle — "broadcasts modelWasChanged" It consumes modelWasChanged and sends viewWasChanged (ModelWasChangedVerticle.java:11–22). It never sends modelWasChanged.
CanvasWasChangedVerticle — "broadcasts canvasWasChanged" It consumes canvasWasChanged and sends modelWasChanged (CanvasWasChangedVerticle.java:12–34). It never sends canvasWasChanged.
Keymap — "maps keyboard events to actions, organized by mode"; KeymapHandler "dispatches key events through mode-specific routing" The KeymapMap is keyed by EditorSubmode (KeymapMap.java:10), and dispatch reads the top of the submode stack (KeyWasPressedVerticle.java:22–24). The model slot is even named modeToKeymap while holding the submode-keyed map (EditorModelCoupler.java:128–130).
Wiki bus-event.md: "modelWasChanged — Server → Server: internal notification" True for the server's own send, but the browser also registers a handler for it and re-sends it: it is both an internal address and a browser-relayed one (§4).

7. Retrieval Practice: Trace Both Paths

Pick the address for each hop from memory. A wrong pick is marked and you can try again; the receiver, payload, and reasoning appear when you are right. Switch traces between the boot path and a keystroke.

Hands-on (10 min): watch the wire.
  1. Build and run: ./gradlew fatJar then java -jar build/libs/visur-1.0.0-SNAPSHOT-fat.jar. Open http://localhost:8888 (it 302s to /static/visur.html).
  2. DevTools → console. The page creates a global eb (var eb = new EventBus(…), visur.js:46). Inject a keystroke without pressing a key: eb.send("keyWasPressed", JSON.stringify({key:"j"})). The cursor should move down one line and "modelWasChanged message: …" should print — you are standing in the relay of §4.
  3. Re-send the canvas size and watch the footer's wrap and SPAN text change: eb.send("canvasWasChanged", JSON.stringify({width:40,height:20})).
  4. Prove ca is dead on the client: grep -n "\bca\b" src/main/resources/static/visur.js returns only its declaration and its one assignment.
  5. Watch a payload land: eb.registerHandler("viewWasChanged", (e,m) => console.log(m.body)) and press a key.

9. Primary Source

This lesson's ground truth is small enough to read completely; read these four in order, in one sitting:

  1. BusEvent.java — four values, four direction comments. The whole protocol in 15 lines.
  2. visur.js — the production client. Read eb.onopen ( 46–121), sendKeyPressedEvent (123–134), and drawCanvas (136–173). Everything above the canvas is state assignment.
  3. ModelWasChangedVerticle.java — the real view model, and the only place View is used.
  4. MainVerticle.java:30–66 — the bridge permissions. Compare them line by line with BusEvent; every permission has exactly one sender.

For the framework layer under §§1 and 4 the primary sources are the Vert.x 4.4.4 classes themselves: EventBusImpl (point-to-point delivery and round-robin handler choice) and EventBusBridgeImpl (how registerHandler becomes a local consumer). Do not take Visur's behaviour on faith from this lesson — both files are short and settle §4 definitively.

A useful external analogy for the whole design is a remote procedure call with a server-push channel: the client sends a request (keyWasPressed), the server replies on a different channel (viewWasChanged), and the client holds no model of its own. The difference here is that the server pushes the whole snapshot rather than a delta, so there is nothing to reconcile.

10. Key Takeaways

  • Four addresses, one ring. keyWasPressed and canvasWasChanged are inbound, viewWasChanged is outbound, and modelWasChanged is the internal hinge — sent by both the keystroke verticle and the canvas verticle, and (see below) by the browser too.
  • Each of the three verticles consumes one address and sends a different one. Nothing in Visur broadcasts or publishes.
  • The view model is an inline JsonObject in toJson(). View is a two-field scratch object, and its ca field is dead weight on the client.
  • Routing is by submode, not mode. getEditorSubmode() peeks the stack; the KeymapHandler array is only the per-submode fallback that turns arbitrary characters into commands.
  • Every keystroke produces a snapshot, even a no-op. The client never predicts the next state; it is a pure function of the last payload.
  • modelWasChanged is relayed by the browser, because send picks one of two local handlers once the bridge has registered a consumer for the outbound registration.
  • The renderer is stateless and has its own canvasWidth, computed differently from the server's. Wrap agreement between the two is a coincidence to verify, not a contract.
