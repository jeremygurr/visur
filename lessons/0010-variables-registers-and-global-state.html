Lesson 10 of 10

Named Slots: The Global Variable Map

Reads ~16 min · Hands-on: run a compiled command sentence token by token, with instant feedback

Lesson 9 ended with a snapshot built from emc.getSpan(), emc.getCursorQuantum(), and friends. Those getters do not read editor-model fields — they read a single HashMap<String, VisurVar> called the global variable map. This lesson opens it. The surprise: the map is not just storage. It is a set of named stack slots that command sentences use to save and restore editor state, and one of its entries — nl — is the very brick the coordinate system reads in Lessons 7 and 8.

Mission Anchor

The mission asks you to predict mode and cursor behavior for any key and to place any operator in its taxonomy. Both are impossible without this map: the i binding is a 14-token program that parks the current span and cursorQuantum in the map, and Escape is the mirror program that restores them and cleans up. This is the last piece of shared state in the system.

Goal this lesson: Name every entry in the global variable map and the class that wraps it; explain why there are exactly two VisurVar implementations rather than three; read a command sentence as a stack program; and say exactly how the map reaches the browser (it doesn't — its values are copied into snapshot fields).

1. One Map, Ten Names

"Global variable" is a storage location, not a synonym for "global state".

2. Two Implementations, Not Three

VisurVar is an interface — a value with getVal and putVal — and it has exactly two implementors in the tree:

VisurVar.java:5–12 · ObjectVisurVar.java:5–24 · BrickVisurVar.java:8–41.

The distinction matters because a BrickVisurVar is live. Its getVal() does not read a stored field; it asks the brick to compute itself first if it is not yet filled in:

BrickVisurVar.java:20–25 · ObjectVisurVar.java:16–18 · Reference: Data Class Map.

Itinerary correction. Lesson 10's itinerary claims "three variable categories: primitives (numbers), objects, bricks". The source has two implementations. Integers are not a category — an span of 1 is an ObjectVisurVar wrapping an Integer, exactly like a Quantum is an ObjectVisurVar wrapping a Quantum. The real split is brick-backed (calculated) vs. object-backed (literal).

There is one asymmetry worth flagging. VisurVar.putVal returns a Result; BrickVisurVar.putVal returns Result.make(), but ObjectVisurVar.putVal returns null (ObjectVisurVar.java:20–24). Nothing reads the return value, so it is harmless — but it is inconsistent.

3. The Two-Layer API: VariableMap → EditorModelCoupler

Nothing else touches the map directly except the three variable operators. Every *Op and service goes through EditorModelCoupler, which resolves the map out of the editor model and delegates to EditorContentService:

EditorModelCoupler.java:40–46 · lines 188–190 · EditorContentService.java:24–30 · lines 76–83.

The typed accessors are the interesting part. getCA, getCX, and getCY cast the variable to BrickVisurVar; getSpan, getCursorQuantum, and getScopeQuantum cast to ObjectVisurVar. A wrong cast would be a ClassCastException at runtime, so the wrapper class is part of the contract for each name:

AccessorExpectsThen
getCA() / getCX() / getCY()BrickVisurVar(int) bvv.getVal() — triggers getOrCalc()
getSpan()ObjectVisurVar(int) ovv.getVal()
getCursorQuantum() / getScopeQuantum()ObjectVisurVar(Quantum) ovv.getVal()
getNextLineIndices()BrickVisurVar(ArrayList<Integer>) bvv.getVal()

EditorModelCoupler.java:56–73 · lines 156–178 · EditorContentService.java:39–41.

Note the write path for the brick variables: putCA does bvv.putVal(ca) and then putGlobalVar("ca", bvv) — re-putting the same object into the map. putVal mutates the brick in place; the putGlobalVar is a redundant write of the same reference. The object-backed writers, by contrast, build a new wrapper each time (ObjectVisurVar.make(...)).

EditorModelCoupler.java:200–216 · lines 295–299 · lines 329–336.

4. nl: The Variable the Coordinates Read

Recall from Lesson 8 that ca ↔ cx/cy conversion happens in CoordinatesDC.calcInternal, computed from a shared read-only nl brick. That brick is the global variable nl:

InitializerService.java:122–142 · EditorContentService.java:86–101 · PrimitiveDataClassBrick.put:80–88 · Reference: Cursor Coordinates Map.

So the sequence at startup is: initializeCursorPositionDCBsAndBVVs() creates the incomplete nl and its wrappers, then emc.initializeEditorContent(...) stores the text, then emc.updateNextLineIndices() computes nl's value. Note that initializeEditorContent does not update nl — only putEditorContent does. The initializer calls the two steps separately.

5. Variables in the Command Language: A Stack Program

Lesson 3 showed that CommandCompileService turns a sentence into a VisurCommand — a parallel list of Operators and opInfo. Lesson 10 adds the missing half: CommandExecutionService runs those operators in order against a stack, the ExecutionDataStack. Three word types exist specifically for variables:

WordWritten asCompiles toStack effect
LiteralStringWord "span" LiteralStringOp push span (quotes stripped)
AssignmentWord -> AssignmentOp pop target, pop source → vars[target] := vars[source]
RecallWord a bare name that is a global var RecallOp push vars[name]
NativeOpWord removeGlobalVar RemoveGlobalVarOp pop name → delete from the map

LiteralStringWord.java:8–20 · LiteralStringOp.java:10–18 · AssignmentWord.java:8–19 · AssignmentOp.java:12–27 · RecallWord.java:8–26 · RecallOp.java:8–13 · RemoveGlobalVarOp.java:4–11.

The word order matters. CommandCompileService tries LiteralNumberWord, LiteralStringWord, AssignmentWord, NativeOpWord, then RecallWord — and RecallWord is the catch-all that matches any non-space token, succeeding only if it names an existing variable:

CommandCompileService.java:10–40 · RecallWord.java:15–21.

The regex reads backwards — the operand is on the left. AssignmentWord's pattern is (->*[^\s]+)(.*), but because [^\s]+ backtracks when the next character is a space, the matched token is just ->. The opInfo it computes (substring(2)) is empty, and AssignmentOp ignores it anyway. All the meaning is in the two names already on the stack: "source" "target" -> copies source into target (AssignmentOp.java:16–17).

6. Save and Restore: Globals as Registers

The itinerary's title says "Variables, Registers, and Global State". There is no separate register file — the registers are global variables. The i binding is the clearest proof:

InitializerService.java:263–265.

Escape in insert and replace mode is the mirror image — restore, then remove the registers:

InitializerService.java:333–336 · lines 363–365.

Why use the global map at all? The stack does not survive between keystrokes; each keystroke compiles and executes a fresh VisurCommand. To carry a value from the i press to a later Escape, it must live somewhere durable. The global variable map is that somewhere — and the temporary names are a precisely-scoped convention on top of it.

An observation on leftovers

Trace the i sentence carefully and you will find that the "character" pushed immediately before quantumStart is never consumed: QuantumStartOp reads the cursorQuantum variable and does not touch the stack (QuantumStartOp.java:8–13). One "character" therefore remains on the execution-data stack after each i. Commands that use the stack defensively (for example f, which begins with clearEDS) are unaffected, but the sentence does leak. This is verified from the source; whether it was intended is a question for the author.

InitializerService.java:264 · QuantumStartOp.java:8–13 · ClearEDSOp.java:7–13.

7. What the Browser Sees: Nothing Directly

The itinerary says "how the frontend reads and displays global state". It does not. A search of visur.js for variable/VariableMap/global returns nothing, and the View class carries only ca and editorContent. Variables reach the browser only as copied fields of the snapshot:

Snapshot fieldLine in toJson()Comes from variable

ModelWasChangedVerticle.toJson():24–52 · View.java:3–6 · visur.js (no variable references).

The map is a server-side implementation detail. The client never sees a name, only the resolved value it needs to draw. This is why adding a variable is safe from the client's point of view — but it also means a variable that nothing copies into toJson() is invisible to the user.

8. Itinerary and Wiki Corrections

The itinerary saysWhat the code does
"Three variable categories: primitives (numbers), objects, bricks" Two implementations: ObjectVisurVar and BrickVisurVar (ObjectVisurVar.java:5, BrickVisurVar.java:8). Integers are ObjectVisurVar values.
"VisurVar — base interface for variables" It is an interface, but it also declares a static make() returning null (VisurVar.java:9–11) — dead code. It is not abstract in any meaningful sense.
"The nl (next line indices) global variable — computed from editor content" Correct — and more: it is the same read-only brick shared by both coordinate decompositions, which is what makes Lesson 8 work (InitializerService.java:125–138).
"How the frontend reads and displays global state" It does not. Five snapshot fields are copied from variables in toJson(); the map itself never crosses the wire.
"register" (in the title) No register concept exists. Registers are global variables named by convention (tempSpan, tempCursorQuantum).

12. Key Takeaways

  • One map, ten names. A single HashMap<String, VisurVar> on the editor model; eight permanent entries plus two transient registers.
  • Two wrappers, not three. ObjectVisurVar is a box; BrickVisurVar is a live window onto the data-class calculation graph.
  • The wrapper class is part of each name's contract. ca/cx/cy/nl are bricks; span/cursorQuantum/scopeQuantum are objects.
  • Commands are stack programs. Literals and numbers push; -> copies one variable into another (source left, target right); a bare variable name recalls its value; operators pop and push.
  • Variables are registers because the stack does not persist. i parks span and cursorQuantum in tempSpan/tempCursorQuantum; Escape restores and deletes them.
  • nl is the bridge to the coordinate system. One read-only brick, computed on every content write, shared by both decompositions.
  • The browser never sees the map. Five snapshot fields are copied from variables; the names stay on the server.
