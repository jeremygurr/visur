The Editor Lifecycle: One Complete Request

Reads ~18 min · Hands-on: trace one keypress in 10 min

Mission Anchor

You are a Java developer learning to work inside the Visur codebase. In Lesson 1 you saw the shape of the system. Now you need the one path every feature travels: a keystroke in the browser becomes a JavaScript event, crosses the network to a Vert.x verticle, is looked up in a keymap, executed by an operator, written into shared state, and finally rendered back onto the canvas.

Almost every change you will ever make to Visur—a new key binding, a new editing action, a new piece of view state—touches this loop. If you can trace it end to end, you can navigate the codebase with confidence. This lesson is that trace.

Goal this lesson: Follow one complete keystroke (j, move down one line) from the browser, through the EventBus, through the KeyWasPressedVerticle, the keymap, and the RelativeMoveOp, into the EditorModelCoupler, back out through the ModelWasChangedVerticle, and onto the canvas—naming every class and method on the way.

2. Shared State: The EditorModelCoupler

The loop only works because all three verticles read and write one shared state object—the EditorModelCoupler (EditorModelCoupler.java, line 14). It is constructed once, in ServiceHolder, and every verticle reaches it through the static field ServiceHolder.editorModelCoupler.

Internally it is a Vert.x LocalMap<EditorModelKey, Object> obtained from SharedData:

That split matters when you go looking for a value. There are two ways in:

  • Direct LocalMap access for framework-level state: editorModel.get(canvasStart), editorModel.get(editorMode). These are read through typed getters such as getCanvasStart() and getEditorMode().
  • Global-variable access for anything the command language can name: getGlobalVar("ca"), getGlobalVar("span"). The coupler exposes typed convenience methods (getCA(), getCX(), getCY(), getSpan(), getCursorQuantum()) that unwrap the variable for you.
Why the coupler is a façade, not a plain map. Callers never touch the LocalMap directly outside EditorContentService. The coupler hides the two-storage split and the repeated casting that the untyped Object values require. If you add a piece of state, add it to the coupler—not to a verticle.

2.1 The EditorModelKey typed key system

The LocalMap is untyped at the value end, but the key end is strongly typed by the EditorModelKey enum:

Because the values are Object, every getter casts on the way out (for example getCA() at EditorModelCoupler.java:56 casts to a BrickVisurVar and calls getVal()). This is the price of a single generic store; the typed keys carry the names, the getters carry the types.

If the coupler is the state, ServiceHolder is the registry of behavior. Its constructor runs once, during MainVerticle.start(), and assigns every service to a public static field:

The static fields are how a verticle reaches a service without dependency injection. In KeyWasPressedVerticle you will see it as ServiceHolder.editorModelCoupler and ServiceHolder.commandExecutionService. This is deliberate and works because Visur is a single-JVM, single-threaded-per-event-loop application.

4. InitializerService: One-Time Setup

InitializerService is where the editor is born. Its constructor calls initializeEditorModel() (InitializerService.java:28), which populates the coupler in a fixed order:

  1. Create the empty VariableMap and store it under globalVariableMap.
  2. Set the starting mode to navigate, and push navigate onto the submode stack (lines 32–36).
  3. Build the cursor-position data-class bricks and the global variables nl, ca, cx, cy (initializeCursorPositionDCBsAndBVVs(), line 122).
  4. Load the initial document text (the Declaration of Independence) and compute the newline index list nl (lines 97–98).
  5. Initialize the quantums (initializeQuantums(), line 157): register the four quantum types and set the starting cursor and scope quantums.
  6. Build every keymap and register them by submode (initializeKeymaps(), line 185).

The payoff of this design is performance: by the time a key is pressed, all the parsing already happened. Keymap.get() returns a ready-to-run VisurCommand.

5. EditorContentService: The Read/Write Helper

EditorContentService (note: it lives in the CursorPositionDC package, not com.ple.visur) is the only class that touches the raw LocalMap besides the coupler. It is stateless—every method takes the LocalMap as a parameter. That makes it trivially testable and safe to share.

Its responsibilities are narrow and mechanical:

  • getEditorContent(editorModel) / putEditorContent(...)— read and write the document text. Note that putEditorContent immediately calls updateNextLineIndices(...), so the newline index list nl can never drift out of sync with the text (EditorContentService.java:67).
  • getGlobalVar(name, editorModel) / putGlobalVar(...)—read and write entries in the nested VariableMap.
  • updateNextLineIndices(...)—recompute nl from the text (EditorContentService.java:86).
  • getCanvasWidth/getCanvasHeight—viewport dimensions, written by ViewportWasChangedVerticle.
Design lesson: keeping the raw-map mechanics in one stateless service means the coupler stays a readable façade and the data plumbing is centralized. When you add state that belongs in a global variable, add the accessor here, then expose a typed method on the coupler.

Aside: the loop also runs at startup

A client declares viewportWasChanged with cell-valued cols and rows. ViewportWasChangedVerticle stores the viewport and triggers modelWasChanged with full:true; the model verticle publishes the first complete view. The browser uses SockJS at /eventbus; the Rust terminal uses plain JSON WebSocket at /ws. There is no browser relay.

9. Key Takeaways

  • The loop is seven steps: keydown → keyWasPressed → handle() → keymap lookup → execute operators → modelWasChanged → viewWasChanged → redraw.
  • State has one home: the EditorModelCoupler, a façade over a LocalMap<EditorModelKey, Object> and a nested VariableMap of global variables.
  • Keys are typed, values are not: EditorModelKey gives compile-checked names; getters perform the casts.
  • Behavior is registered once: ServiceHolder wires every service, and InitializerService populates state and compiles every keymap at startup.
  • Messages carry signals, not state: modelWasChanged is sent with a null body; readers go back to the coupler for the data.
  • Parsing is precomputed: a keypress is a hash-map lookup into an already-compiled VisurCommand.
