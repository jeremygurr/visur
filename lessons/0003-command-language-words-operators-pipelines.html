The Command Language: Words, Operators, and Pipelines

Reads ~20 min · Hands-on: compile & trace a command in 10 min

Mission Anchor

In Lesson 2 you watched a keypress travel through the editor and stop at this line: the keymap hands the KeyWasPressedVerticle a VisurCommand, and CommandExecutionService runs it. This lesson opens that command up.

Almost every feature you will add to Visur—a new editing action, a new key binding, a new compound gesture like "span" pushSubmode—is written in this small language. If you can read and write Visur command strings, you can extend the editor without touching a single line of Java. That is the leverage this lesson gives you.

Goal this lesson: Understand the two-phase pipeline (compile then execute), name the four word types that tokenize a command string, explain why operands travel on an ExecutionDataStack instead of as Java arguments, and hand-compile the real command "span" "tempSpan" -> 0 setSpan.

1. The Big Idea: Visur Is a Stack Language

Before any class names, hold on to one idea. The Visur command language is a concatenative, stack-based language—a thin cousin of Forth and PostScript. There are no parentheses and no named arguments. Instead:

  • Literals push. A number or a quoted string pushes its value onto a shared stack.
  • Operators pop. An action takes its operands off the top of the same stack, does its work, and (usually) pushes a result back.
  • Order is everything. 5 j and j 5 are different programs, exactly as they are in Forth.

The stack is a real object—ExecutionDataStack.java—a plain Stack<Object> with push, pop, peek, and size. It is stored in the shared editor model, so every operator reaches it through EditorModelCoupler.getExecutionDataStack().

Why a stack, and not Java arguments? A method call like relativeMove(dx, dy) needs a Java caller that already knows the argument types. A stack lets the same generic executor run any command: it just walks a list of operators, and each one pulls whatever it needs off the shared stack. This is what makes the keymaps data—strings compiled at startup—rather than code (Lesson 2, §4).

3. The Four Words (and the Fifth)

A Word is a lexical token class. Each Word implementation tries its own regex against the front of the remaining sentence; the first one that matches claims the token and reports what operator it produced. Visur registers five word types—the itinerary names four, but the compiled list in CommandCompileService.java includes a fifth, RecallWord, which is how global-variable names enter a command.

WordMatchesProducesopInfo
LiteralNumberWord 5, -1, 3.14 LiteralNumberOp the parsed number
LiteralStringWord "span" LiteralStringOp the quoted text
AssignmentWord -> AssignmentOp the text after the arrow

RecallWord previousSearchTarget RecallOp the variable name

RecallWord — global-variable names

RecallWord is the catch-all at the end of the list. It takes the next token and asks: is this the name of a global variable? If yes, it emits a RecallOp whose job is to push that variable's value. If no, it returns null—which, because RecallWord is last, ends compilation.

Note the ordering rule. CommandCompileService tries the words in array order and stops at the first match (CommandCompileService.java:22–28). NativeOpWord and RecallWord use the same ([^\\s]+) pattern, so order decides who wins: a native operator name is claimed first; only if it is not a known operator does RecallWord get a chance. Arrays are load-bearing here.

4. Compiling: The Loop That Builds a VisurCommand

CommandCompileService.compile() is a lazy tokenizer: no lexer, no grammar, no AST. It simply loops while text remains, asks each word to claim the front of the string, appends what comes back, and repeats.

CompiledWordResponse is the handoff object between the two halves of the compile phase. It carries exactly three fields (CompiledWordResponse.java:2–4): Operator op, Object opInfo, and String remainingSentence. It is the currency of every Word.

An assignment: the prefix of the i key

Three lessons fall out of these traces. First, values travel on the stack: the names span and tempSpan are just strings pushed by literals, and configuration values like "insert" and "character" ride the same stack as numbers. Second, the -> marker is only syntax—the real arguments are the two names pushed before it. Third, a well-formed command should leave the stack balanced; where that is hard to guarantee, clearEDS (ClearEDSOp) is bound at the start of a gesture to reset the stack to a known state.

7. CommandStateService: The Command Line

Everything so far assumes the sentence was typed all at once, because that is how the running editor works: every command comes from a precompiled keymap. There is also a second, live code path. When isInCommandState is true, KeyWasPressedVerticle routes keystrokes to CommandStateService instead of the keymap (the branch you saw in Lesson 2, Step 1).

CommandStateService is a fully implemented prompt with no UI entry point yet—so the behavior below is what the code does, not a binding you can reach by pressing a key today.

10. Primary Source

The highest-trust account of this lesson is the code. Read these three files top to bottom, in this order:

  1. CommandCompileService.java—the entire compiler is one loop.
  2. NativeOpWord.java—the complete instruction-name-to-class table.
  3. CommandExecutionService.java—the entire executor is one loop.

For the underlying language concept, read the Wikipedia article on stack-oriented programming and the Forth page it links to. Visur's language is not Forth, but the mental model—postfix order, one shared data stack, words as functions—is exactly the same, and it makes the code read as familiar rather than exotic.

For wisdom—the judgment of how a command language should be designed—the Forth community is the deepest well. The Forth 2012 standard and its mailing list discussion show what designers learned from decades of stack-language use, including the failure modes of implicit operand stacks. 11. Key Takeaways

  • Visur's command language is stack-based: literals push, operators pop, order defines meaning.
  • Compile and execute are separate phases joined by VisurCommand—a parallel list of operators and operands.
  • Five words tokenize a command: LiteralNumberWord, LiteralStringWord, AssignmentWord, NativeOpWord, and RecallWord; the first match in array order wins.
  • NativeOpWord's switch is the instruction set; a new editing action is a new case plus one Operator class.
  • Operands travel on the ExecutionDataStack, not in Java arguments—this is what lets the executor stay generic.
  • A keymap is a precompiled command; the ; prompt compiles the same way at runtime.
