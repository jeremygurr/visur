Cursor Position: One Fact, Two Coordinate Systems

Reads ~18 min · Hands-on: convert ca ↔ (cx, cy) with instant feedback in the coordinate lab

The cursor is one point. Visur tracks it as an absolute character index (ca) and, separately, as a logical line and column (cx, cy). Only one of those representations is allowed to be set at a time—and the whole editor stays consistent because the other one can always be derived on demand from a shared, read-only list of newline positions. This lesson is that trick, applied to the cursor.

Mission Anchor

Lesson 7 ended on the observation that ca can be computed from cx, cy, and nl "without ever being assigned", and that nl is a read-only leaf shared by two different calculi. That was the general machinery. Here it gets a purpose: moving the cursor cleanly in a wrapped document.

The itinerary calls this lesson "cursor position management"—and then lists a rendering subsystem (Coordinate, ViewCell, VisurColor, a LineWrapping service). Most of that subsystem does not exist yet. This lesson separates the part that is real and load-bearing from the stubs, so you do not go looking for behavior that was never written.

Goal this lesson: Given nl = [12, 25, 32] and any one of ca or (cx, cy), produce the other by hand, and say which half of the coordinate graph is currently materialized. Then name the three coordinate spaces the editor actually uses and why cx is not a screen column.

3. Nothing Is Assigned; Everything Is Derived on Read

putCA writes exactly one value: the ca brick. putCX and putCY write their bricks. No method recomputes the other representation as a side effect.

The subtle part: cacheVal writes the derived value directly and does not call put, so it does not run conflict resolution. After you read cx, both caAndNLDCB and cxcyAndNLDCB can report complete at the same time. The "only one decomposition" rule is enforced on the next real put, not on a read. Lesson 7's test asserts exactly this—see getOrCalc in TestCursorPositionDC.java:266–343.

4. A Keystroke That Flips the Graph: j

Put the two halves together. Press j (move down one line) and the cursor position flips from the ca decomposition to the cx/cy decomposition and back.

RelativeMoveOp.java:11–26 · CharacterQuantum.java:58–92 · EditorModelCoupler.java:200–218 · MovementVector.java.

This is why CursorPositionDC needed two decompositions rather than one: vertical movement is naturally expressed in cx/ cy (preserve the column, change the line), while document operations—search, quantums, bounds—are naturally expressed in the absolute ca.

5. From Logical Coordinates to the Screen

cx is not a screen column. It is a column within a logical line. When a logical line is wider than the viewport it wraps into several short lines, and cx keeps counting across them.

What the itinerary gets wrong about display

Itinerary saysActually
LineWrapping — "line wrapping management service" A two-value enum {wrapped, unwrapped}. It is stored by InitializerService and readable through getLineWrapping(), but no code branches on it. The real wrapping math is canvasWidth + RelativeLineBoundCalculator + the scroll logic.
Coordinate — "immutable coordinate for canvas rendering" An unused stub: a private constructor, a make(x, y) factory, equals, and hashCode. It is never constructed anywhere in src/main or src/test.
ViewCell — "how a single character is displayed" An unused stub holding a char and foreground/background colors; its constructor sets only the character. Nothing builds one.
VisurColor — "color model for canvas visualization" An unused stub with a single String color field. There is no color model.
MovementVector — "relative cursor movement (dx, dy)" Real and used. Public dx/dy fields, built by RelativeMoveOp for every motion, consumed by each quantum's move().
Why this matters: if you are looking for where Visur decides how to paint a wrapped line, do not start at LineWrapping or ViewCell. Start at the scroll methods putCursorQuantumStartAndScroll / putCursorQuantumEndAndScroll and the canvasStart / virtualCX state, then follow the front end in visur.js (Lesson 9).

7. Primary Source

The highest-trust account of this system is the code pair—the calculator and its test. Read them together; each is short:

  1. CoordinatesDC.java— calcInternal, calcCAAndNL, and calcCXCYAndNL. This is the entire coordinate model in about forty lines.
  2. TestCursorPositionDC.java— the executable specification. Read isComplete and getOrCalc first: they show both decompositions completing after a read, which is the non-obvious behavior.
  3. CursorPositionDCHolder.java— the wiring: how nl is shared and which requiredSetValues each compound gets.
  4. RelativeLineBoundCalculator.java— the long/short line split that makes cx a logical column.

For the underlying idea—keeping one canonical value and deriving views on demand—the closest well-known analogue is a database's index: the table is the truth, the index is a derived structure materialized only when used, and both describe the same rows. Visur's ca is the table; (cx, cy) is the index; requiredSetValues = 1 keeps them from disagreeing.

8. Key Takeaways

  • One persisted fact, two descriptions. ca and (cx, cy) compete for the single slot coordinatesDCB allows; nl is shared and read-only.
  • Both formulas live in one place: CoordinatesDC.calcInternal. The CAAndNLDC/CXCYAndNLDC sub-compounds are just containers.
  • Reads trigger conversion. put never recomputes; BrickVisurVar.getVal → getOrCalc does, and caches the result without running conflict resolution.
  • A vertical move uses both directions. j derives cx/cy from ca, writes them (dropping ca), then derives ca back.
  • cx is a long-line column, not a screen cell; wrapping lives in canvasWidth, RelativeLineBoundCalculator, and virtualCX.
  • LineWrapping, Coordinate, ViewCell, and VisurColor are stubs. Only MovementVector from the itinerary's display list is real.
