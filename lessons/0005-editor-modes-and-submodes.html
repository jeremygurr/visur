Editor Modes and Submodes: The Context Layer

Reads ~20 min · Hands-on: trace one submode from entry to exit

Mission Anchor

Lesson 4 ended on a set of operators that exist only to change context: ChangeModeOp, PushSubmodeOp, RemoveSubmodeOp, ChangeScopeOp, SetSpanOp. This lesson follows that context layer, because it is the answer to a question you will hit constantly while reading Visur: why did pressing the same key do something different a moment ago?

The itinerary describes "3 modes: Normal, Replace, Insert" and "6 submodes." The code tells a slightly different story, and the difference is the whole lesson. There are two parallel enums, only one of them routes keystrokes, and one of the itinerary's three "modes" is not a mode at all. Getting this straight is what makes the rest of the editor legible.

Goal this lesson: Given any keypress, say which state value selected its handler, and predict the next submode. Correct the itinerary's mode/submode counts against the two enums, and name the two classes that look like the context layer but are dead code.

Count check. Itinerary: 3 modes + 6 submodes. Reality: 3 EditorModes + 9 EditorSubmodes, and the sets overlap on two names. Do not try to make the two lists disjoint—the overlap is real and is exploited in §4.

This is why a normal-mode i compiles "insert" changeMode: the string is a valid name in both enums, so the mode becomes insert and the submode insert is pushed in one step. Walk the three entry bindings and the one exit binding:

Bindings at InitializerService.java:263–288 (navigate keymap) and 333–364 (insert/replace keymaps).

The o key is the tell. EditorMode.getModeByString("replace") returns null, so ChangeModeOp skips putEditorMode. The mode stays navigate while the submode becomes replace. This is the concrete proof that replace is not a mode—and it is why the status bar (§5) prints "REPLACE SUBMODE", not "REPLACE MODE".

6. Every Submode, Entry to Exit

Each of the nine submodes has exactly one handler. The handler does not itself edit anything—like the mode handlers from Lesson 4, it compiles a command and hands it back. This table is the map:

insert i, a "c" insertChar 1 0 relativeMove Escape

9. Primary Source

The code is again the highest-trust account, and the files are tiny. Read in this order:

  1. EditorMode.java and EditorSubmode.java—read the two enums side by side; they are 15 lines each.
  2. ChangeModeOp.java + PushSubmodeOp.java—the peek/delegate/pop split that reconciles the two enums.
  3. KeyWasPressedVerticle.java—the single routing line, in context.

For the underlying design idea—a modal editing interface where the same key means different things in different states—the deepest well is Vim's own documentation: Vim's insert.txt for insert/replace mode, and intro.txt for the overall mode model. Compare Vim's modes (normal, insert, visual, operator-pending, command-line, replace) against Visur's mode+submode pair: Vim folds "operator-pending" and "visual" into its mode list, while Visur keeps a small EditorMode and pushes the rest into submodes. That contrast is the most valuable thing to notice here.

For wisdom on whether modes are a good idea at all, the moderation culture on the Vi and Vim Stack Exchange is a living record of practitioners arguing about mode discoverability and muscle memory. Posting a concrete question there—for example about designing operator-pending state—is how you test this model against people who use modal editors daily. If you would rather workshop it locally, say so and we will design a new submode together instead.

10. Key Takeaways

  • Two enums, two layers. EditorMode is a single reported value; EditorSubmode is a stack. Only the submode routes keystrokes.
  • The router is one line: keymapMap.get(emc.getEditorSubmode()), and the map is Map<EditorSubmode, Keymap>.
  • Standardize on the repo's names: the itinerary's "Normal / Replace / Insert" is navigate / a submode / insert. replace is not an EditorMode.
  • changeMode writes both layers—it peeks to set the mode, then delegates the same string to pushSubmode.
  • putEditorSubmode pushes, and pushing navigate resets the stack to one entry.
  • Handlers are fallbacks: explicit keymap bindings win; handlers fill the gaps.
  • Names lie. EditingModeHandler and ModeSwitchService are dead code.
