Lesson 7 of 10

The Data Class Hierarchy: Two Parallel Trees

Reads ~22 min · Hands-on: predict which cursor-position inner survives a put()

Visur stores editor state in a schema-plus-instance type system. Every state value is a brick: a node that knows its type, its name, and every container that holds it. The containers are outer bricks, and each one declares how many of its children must be set. That single number—requiredSetValues—is the hinge the entire conflict-resolution machinery swings on.

Mission Anchor

Lesson 6 ended by pointing at the place nl, ca, cx, and cy actually live. They look like plain model integers, but they are not: nl is a read-only leaf brick shared by two different calculi, and ca can be computed from cx, cy, and nl without ever being assigned. That read-through behavior is the whole reason this hierarchy exists.

The itinerary calls this "a nested type system" with "5 levels of abstraction" and a chain that runs DataClass → DataForm → DataClassBrick → …. That chain is wrong in an instructive way. There are two parallel trees, not one ladder, and DataForm is not on either of them. Correcting the picture is the first half of this lesson.

Goal this lesson: Given a node in the cursor-position graph, name (a) which tree it belongs to, (b) whether it is primitive, compound, or layered, and (c) its requiredSetValues. Then predict, for a put() on one leaf, which sibling inner survives and which is removed.

1. Two Trees, Not One Ladder

The package DataClass defines a type system in the mirror image of a normal class hierarchy. On the left are types (the schema); on the right are instances (the bricks). Each schema kind has a brick kind that mirrors it:

Schema kindBrick kindWhat the brick is
PrimitiveDataClass PrimitiveDataClassBrick A leaf: one value, or empty
CompoundDataClass CompoundDataClassBrick A named map of child bricks
LayeredDataClass LayeredDataClassBrick An ordered stack of compound bricks

PrimitiveDataClass.java:5–12 · CompoundDataClass.java:5–17 · LayeredDataClass.java:5–23 · OuterDataClass.java:7–15.

Correction 1 — the itinerary's "5 levels" are two trees plus an orthogonal value wrapper. The real shape is DataClass → {PrimitiveDataClass, OuterDataClass} and OuterDataClass → {CompoundDataClass, LayeredDataClass}. DataForm is not a level: it is a value type used inside a primitive brick (§4). And the itinerary omits PrimitiveDataClass entirely, which is the schema half of every leaf.

2. The Schema Side: What Each Kind Declares

A schema object is a factory and a rulebook. It holds no runtime state—the same CoordinatesDC instance is shared by every brick made from it.

The hinge: requiredSetValues

This is the one number to remember. A compound is "complete" when at least this many of its inners are set; a layered brick is complete only when every layer is complete (its required count is set to layers.size()). Overfilling—more non-empty inners than required—is what triggers conflict removal.

SchemaConstructor callMeaning
CoordinatesDC new CoordinatesDC(1) exactly one of its two decompositions may be set
CAAndNLDC new CAAndNLDC(2) ca and nl together
CXCYAndNLDC new CXCYAndNLDC(3) cx, cy, and nl together

Constants live in CursorPositionDCHolder.java:8–15. CoordinatesDC = 1 is the "either/or" constraint that makes the bidirectional trick safe (§6).

3. The Brick Side: Nodes That Know Their Outers

Every brick carries three fields, inherited from DataClassBrick: its schema (dc), its name, and an ArrayList of outers—the containers that hold it. The outers list is the inverse of the schema's inners map, and it is what lets a brick walk upward to compute or unset itself.

BrickExtra fieldsDistinguishing behavior
PrimitiveDataClassBrick dfb, isReadOnly put() sets the value, then walks outers removing conflicts
CompoundDataClassBrick inners, cdc removePossibleConflicts() drops inners when overfilled
LayeredDataClassBrick layers, ldc Outers are null; required count is the layer count

Correction 2 — isEmpty() is hand-rolled per brick type. PrimitiveDataClassBrick.isEmpty() is exactly !isComplete(), CompoundDataClassBrick.isEmpty() peeks one level deeper into compound children, and LayeredDataClassBrick.isEmpty() always returns false (LayeredDataClassBrick.java:45–48). 4. DataForm: The Value Type Under a Leaf

A primitive brick's value is not a bare Object. It is wrapped in a DataFormBrick: a DataForm (the type) plus a concrete value. The form decides what counts as valid input and how values convert between representations.

Correction 3 — conversion is declared but not implemented. DataForm advertises convertTo/convertFrom and a convertibleForms array, but every concrete implementation in this repo returns null (JavaIntDF.java:31–39, IntArrayListDF.java:38–46). canConvertTo also short-circuits after the first array entry: its second loop returns on iteration zero (DataForm.java:13–22). Treat forms here as validators that intend to become a conversion system.

The pieces are assembled once, in the holder: CursorPositionDCHolder.java:21–29 wires caAndNLDC.putInner("wholeNumber", wholeNumberDC) and so on. A holder is the schema registry; a brick graph is built from it at startup.

5. The Worked Example: CursorPositionDC

Everything above collapses into one concrete graph. It has exactly one layered class (CursorPositionDC), whose single layer is CoordinatesDC. That layer holds two alternative decompositions of the same cursor:

InnerFieldsWhat setting it means
caAndNLDCB ca, nl "My position is absolute index ca"
cxcyAndNLDCB cx, cy, nl "My position is column cx, row cy"

Because CoordinatesDC requires exactly one decomposition, the graph can never be in an inconsistent state where both disagree. Setting one is a request to switch representations, and that request triggers the conflict machinery of §7.

6. getOrCalc(): Reading Through the Outers

If a leaf is unset, asking for its value does not fail. The brick asks its outers to compute it. This is Visur's substitute for a stored redundant field: the absolute cursor position is never both stored and authoritative; it is whichever representation is set, with the other derived on demand.

Correction 4 — the layered brick's own calc is a landmine. LayeredDataClassBrick.calc calls layers.get(i).getCDC().calcInternal(targetName, this), passing itself—a LayeredDataClassBrick—where CoordinatesDC.calcInternal immediately casts the argument to CompoundDataClassBrick and would throw LayeredDataClassBrick.java:76–85 · CoordinatesDC.java:49–58. The current wiring never reaches it (leaves call their compound outers directly), so it is latent, not live. Notice it: "compiles and passes tests" is not "correct".

7. put() and the Two Conflict Rules

Setting a leaf is not a simple assignment. put(val) writes the value, then walks up through every outer, asking each compound whether it is now overfilled:

The two rules from documentation.txt are both consequences of that single overfill test:

RuleIn one sentenceWhere it lives
Catalyst Permanence A put does not unset a neighbor unless keeping both would overfill some outer. The nonEmpties > required guard
No Outer Left Behind When an outer is overfilled, every inner not on the putting brick's path is removed, and the removal cascades outward. removeInnersAndAllOutersOfInners

(TestCursorPositionDC.java:224–247). It is not a fluke; it is the requiredSetValues = 1 rule working as designed.

Correction 5 — the itinerary's "cascade unset through nested containers" is narrower than it sounds. The cascade only fires from an outer whose own non-empty count exceeds its required count. An outer that is merely incomplete (fewer than required) never removes anything. And the protection set means the brick you put, plus the whole chain of outers you came through, is never among the removed—so put cannot delete the value it just set.

One more subtlety: after unsetting a shared neighbor, calcNeighbor only re-derives neighbors that have more than one outer (outers.size() > 1). Solitary neighbors are assumed to have no alternate decomposition to offer (PrimitiveDataClassBrick.java:155–181).

9. Primary Source

The highest-trust account of this system is the code plus its one design document. Read them in this order—each file is short:

  1. documentation.txt—the six worked ASCII examples of the two conflict rules. This is the single most valuable file; the prose is dense but the diagrams reward a slow read.
  2. PrimitiveDataClassBrick.java—put, getOrCalc, and the protection-set walk.
  3. CompoundDataClassBrick.java—isComplete, getNumberOfNonEmpties, and removePossibleConflicts.
  4. TestCursorPositionDC.java—the executable specification: isComplete, setOuters, putWhenComplete, and getOrCalc show the intended behavior in the smallest possible setting.

For the underlying design idea—representing a schema as data and computing derived fields on read—the closest well-known analogue is the relational model, where a view is defined by its query and never stored redundantly. Visur's caAndNL and cxcyAndNL are two views over the same nl, with requiredSetValues = 1 enforcing that exactly one is materialized at a time. That comparison is the most valuable thing to take from this lesson.

10. Key Takeaways

  • Two parallel trees, not one ladder: schema (DataClass → PrimitiveDataClass, OuterDataClass → CompoundDataClass, LayeredDataClass) beside bricks (DataClassBrick → PrimitiveDataClassBrick, OuterDataClassBrick → CompoundDataClassBrick, LayeredDataClassBrick).
  • DataClass is empty. The itinerary's "specifies fields" belongs to CompoundDataClass.inners.
  • requiredSetValues is the hinge. Compound completion is completeInners >= required; layered completion is all layers complete.
  • DataForm is orthogonal: a validation gate (makeBrick returns Optional) wrapped by DataFormBrick. Conversions are stubbed to null.
  • Bricks carry outers; one brick can have several (nl has two), which is what makes shared derivations possible.
  • getOrCalc reads through the outers; the cursor's ca and cx/cy are mutually derivable, with the math on CoordinatesDC, not on the sub-compounds.
  • put protects its own path. An overfilled outer removes every inner not already in the checked set; read-only bricks such as nl always survive.
