Lesson 4 of 10

Operators: The 30+ Editing Actions

Reads ~22 min · Hands-on: read one operator cold in 5 min

Mission Anchor

Lesson 3 ended on the executor's inner line: currentOp.execute(currentOpInfo). The command language compiles a sentence into a list of operators; this lesson opens the list. Every editing action Visur can perform is one class implementing one method—and once you can read that method, you can read the whole editor.

The itinerary names this "the 30+ editing actions." The exact count is 27 editing operators plus one vestigial service that happens to implement the same interface. This lesson gives you a repeatable way to read any of them, then walks all nine families, then names the stubs and traps that will bite you if you assume the names mean what they say.

Goal this lesson: Read any *Op.java and answer three questions without guessing—what does it take off the stack, does it use the operand the compiler handed it, and what does it write into the editor model. Then name every family and its members.

1. The One Contract

Every operator is the same shape. Operator.java is a one-method interface—the execute-side twin of the compile-side Word from Lesson 3:

Because execute returns nothing and takes almost nothing, all the real communication happens through three channels. Knowing which channel an operator uses tells you nearly everything about it:

The three-question method. To read any operator you do not need to trace its whole body. Ask:
  1. Stack in: does it pop(), peek(), or touch the stack at all? How many pops, and in what order?
  2. opInfo: does it use the operand from the compiler, or ignore it?
  3. Model out: which emc.put…() methods does it call? That is the entire side effect.
The rest is arithmetic. We will use this method on every family below.

3. Literals and the Stack Reset

The two pushers have no keyword—they are created by LiteralNumberWord and LiteralStringWord from Lesson 3. They are the only operators that read nothing and mutate no editor state; their whole job is to put a value on the stack.

OperatorStack inStack outModel out
LiteralNumberOp none pushes opInfo (a number) none
LiteralStringOp none pushes opInfo with quotes stripped none
ClearEDSOp everything empty stack none

ClearEDSOp ("clear execution data stack") is the operator behind the clearEDS keyword. It is a while loop that pops until the stack is empty—a panic button used at the start of gestures that cannot guarantee a balanced stack (the f binding opens with it).

5. Insertion — Why the Handler Moves the Cursor

KeywordOperatorStack inModel out
insertChar InsertCharOp pops the character string editor content
insertNewline InsertNewlineOp none editor content; ca (+1); quantum bounds
replaceChar ReplaceCharOp pops the replacement string editor content (unless the char is a newline)

Here is a subtlety that catches every reader at least once: in insert mode, typing a letter does not go through the keymap. The InsertModeHandler compiles a command on the fly from the keystroke:

InstructionOperator runsStack after
"a"LiteralStringOp[a] (quotes stripped)
insertCharInsertCharOp[] — a spliced in at ca
1LiteralNumberOp[1]
0LiteralNumberOp[1, 0]
relativeMoveRelativeMoveOp[] — cursor moves right one

ReplaceModeHandler does the same thing with replaceChar. InsertNewlineOp is the exception: it manages its own cursor (ca++) and recomputes the quantum bounds, so its binding is just insertNewline.

Rule of thumb: an operator that changes the document but not the cursor usually expects a companion relativeMove in the same command. Check the handler that compiles the command, not the operator alone.

6. Deletion — Two Very Different Powers

KeywordOperatorStack inModel out
deletePreviousChar DeletePreviousCharOp none editor content (keeps ca)
deleteCursorQuantum DeleteCursorQuantumOp none editor content; ca; quantum bounds (only if span > 0)

Backspace is deletePreviousChar followed by an explicit move: the insert keymap binds it to deletePreviousChar -1 0 relativeMove. The operator deletes editorContent[ca-1 .. ca), then writes back the same ca—so the deletion and the move are two separate steps, exactly like insert.

7. Variables — Copy, Recall, Add, Remove

OriginOperatorStack inModel out
-> (AssignmentWord) AssignmentOp pops destination name, then source name global var map (a copied VisurVar)
a variable name (RecallWord) RecallOp none (uses opInfo) pushes the variable's value
+ AddOperator pops a, then b pushes a + b (integers only)
removeGlobalVar RemoveGlobalVarOp pops the variable name global var map (entry removed)

AssignmentOp is the only operator whose pop order the Lesson 3 example depends on: destination first, source second, so the destination name was pushed last. It does not move a reference—it builds a fresh BrickVisurVar or ObjectVisurVar around the value.

RecallOp is the clearest example of the opInfo channel: it never pops, because the compiler already put the variable name into opInfo via RecallWord. It looks the name up and pushes the value.

AddOperator is not a variable operator. Despite living in the "variables" family, it does plain integer addition on the stack: es.push(a + b). It is the + keyword from Lesson 3. There is no operator that adds a value into an existing variable.

8. Mode & State — the Compound Operator

KeywordOperatorStack inModel out
changeMode ChangeModeOp peeks the mode name, then delegates editor mode; also runs PushSubmodeOp
pushSubmode PushSubmodeOp pops the submode name submode stack
removeSubmode RemoveSubmodeOp none submode stack (pops one, never below 1)
changeScope ChangeScopeOp pops the scope quantum name scopeQuantum global
setSpan SetSpanOp pops the span toggle (normalized to 0/1) span; cursorQuantum start & end

ChangeModeOp is compound, and it is the one operator that both peeks and pops the same value. It reads the mode name with peek() (without removing it), sets the editor mode, then calls PushSubmodeOp—which pops that same string and uses it as the submode name:

"Replace" is a submode, not a mode. EditorMode only has navigate, insert, and reading. EditorSubmode has replace. So the o binding ("replace" changeMode …) sets the submode to replace, but getModeByString("replace") returns null, so the mode stays navigate. Replace behavior is driven entirely by the submode. The itinerary's "3 modes (Normal, Replace, Insert)" is true of the keymaps, not of the EditorMode enum.

PushSubmodeOp has one special case: pushing navigate collapses the submode stack down to its first element, so "navigate" pushSubmode is the universal "escape to normal" from any nested submode. RemoveSubmodeOp is the gentler pop—it refuses to empty the stack.

SetSpanOp is worth noting for its normalization: spanToSet = spanToSet > 0 ? 1 : 0. Span is a boolean in disguise—"is there a selection?"—and the operator recomputes the quantum boundaries every time it changes.

11. Two Names That Are Not Operators

Two entries in the itinerary's operator list are not editing operators at all. Do not go looking for behavior in them.

OperatorService — a vestigial registry

OperatorService is an interface: void execute(Operator operator, Object... args). Its only implementation, ModeSwitchService, has a body that is entirely commented out—it throws if it is given arguments, and otherwise does nothing. Nothing in the current codebase calls OperatorService. It reads like an abandoned alternative to the CommandExecutionService pipeline: a place where a service, not the operator itself, would perform an operator's work. Treat it as dead scaffolding.

13. Primary Source

The code is the highest-trust account here, and it is unusually readable because each operator is only 10–40 lines. Read in this order:

  1. Operator.java—the one-method contract.
  2. RelativeMoveOp.java—the fullest small operator: stack in, model out, bounds recompute.
  3. ChangeModeOp.java + PushSubmodeOp.java—the compound operator and the peek/pop split.

For the underlying design idea—an action that mutates shared state through a uniform one-method interface—read the Wikipedia article on the command pattern. Visur's twist is that the "receiver" is one global EditorModelCoupler and the "arguments" are a stack, but the shape—encapsulate each action as an object with a uniform execute—is the classic pattern.

For wisdom on how many operators to have and how to group them, the Vim project is the deepest well: its source exposes motions, operators, and text objects as separate composable axes, whereas Visur folds them into one list. The Vim normal-mode source and its surrounding discussions are worth a skim. If you would rather keep the feedback loop local, say so and we will workshop a new operator end to end together instead.

14. Key Takeaways

  • One interface, 27 operators. execute(Object opInfo); operands come off the ExecutionDataStack, effects go into EditorModelCoupler.
  • Use the three-question method: stack in, opInfo use, model out. It reads any operator in under a minute.
  • Pop order is load-bearing. RelativeMoveOp pops dy then dx, so keymaps push (dx, dy); AssignmentOp pops the destination first.
  • Document-changing operators usually do not move the cursor; the mode handlers append 1 0 relativeMove to compensate.
  • Some operators delegate and hide a pop (QuantumStartOp / QuantumEndOp), and some delegate and hide a whole second operator (ChangeModeOp).
  • "Replace" is a submode, not an EditorMode. getModeByString("replace") returns null, so mode stays navigate.
  • Names lie. AbsoluteMoveOp is empty, OperatorService is dead, and AddOperator is integer addition, not variable addition.
